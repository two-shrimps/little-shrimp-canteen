# Little Shrimp Canteen 实践与实施记录

> 版本：v0.4
> 创建日期：2026-10-22  
> 当前阶段：阶段 0——技术预研与工程决策
> 文档性质：持续更新的执行手册、进度记录与决策日志

## 1. 文档目的

这份文档用于指导 Little Shrimp Canteen 从原型走向可使用的 App，并持续记录实施过程中的方案调整、实验结果、技术决策和未解决问题。

它不是一次写完后不再变化的技术方案，而是项目的“实践账本”。每完成一个步骤，我们都应该在这里留下：

- 做了什么。
- 为什么这样做。
- 如何验证。
- 结果是否符合预期。
- 哪些产品或技术假设发生了变化。
- 下一步是什么。

最终目标不是按原计划完成所有功能，而是持续缩短这条真实闭环：

```text
小红书菜谱截图
      ↓
AI 整理并人工确认
      ↓
加入今晚或其他日期的菜单
      ↓
生成并完成采购清单
      ↓
保存做菜照片和分角色评价
      ↓
在餐桌时间线中留下记录
```

## 3. 协作与记录原则

### 3.1 一次只推进一个可验证步骤

每个步骤应该小到可以明确判断完成或失败。避免一次同时实现整个菜单、采购和分享系统。

推荐节奏：

```text
选择一个小目标 → 写清验收标准 → 实现 → 自动验证 → 真机体验
               → 记录结果与调整 → 选择下一步
```

### 3.2 纵向闭环优先于横向完整

优先让一条简单流程真正可用，再增加各模块的高级能力。第一条闭环可以只支持：

- 一个餐桌空间。
- 一个登录账号。
- 一个可选的非登录同桌档案。
- 从相册选择截图。
- 人工确认 AI 结果。
- 一顿晚餐。
- 手动采购勾选与金额。
- 一张成品照片和一个综合评分。

### 3.3 方案状态必须显式标记

本文档中的重要方案使用以下状态：

| 状态 | 含义 |
| --- | --- |
| `已确定` | 已经过讨论或实践验证，按此实施 |
| `暂定` | 当前默认方案，可以先做，但仍可能调整 |
| `待验证` | 需要用原型、代码或真实用户验证 |
| `已否决` | 明确不采用，并保留原因 |
| `已替换` | 曾经采用，后来被新方案取代 |

### 3.4 不静默改变产品行为

实现中遇到以下情况时，需要更新产品原型文档或本文档：

- 页面流程发生变化。
- 字段含义或必填规则变化。
- AI 能力边界变化。
- MVP 范围增加或删除。
- 数据模型迫使产品行为改变。
- 真机使用证明原设计不好用。

小型代码重构、内部命名和不影响体验的实现细节无需上升为产品决策。

### 3.5 每一步必须有验证

根据变更类型至少完成一种验证：

- 业务逻辑：单元测试。
- 数据读写：集成测试和迁移测试。
- 页面交互：组件测试或端到端测试。
- 相机、相册、分享和通知：真机测试。
- AI 输出：固定样本评测和人工复核。
- 视觉：与 Figma 对照并检查不同屏幕尺寸。

## 5. MVP 成功标准

第一版不是以页面数量验收，而是以真实任务验收。

### 5.1 核心验收故事

> 用户登录自己的账号，从相册选择一组小红书菜谱截图，AI 提取菜名、食材和步骤；用户修正不确定项并保存，将菜谱加入今晚菜单。系统按照两人份生成合并后的采购清单。用户可以边买边勾选、补充临时商品和记录金额。做完后上传照片，为自己和可选同桌档案分别记录评分，并在餐桌历史中再次找到这次记录。

### 5.2 MVP 完成条件

- [ ] 一个真实账号可以登录并在一台目标手机上稳定使用。
- [ ] 菜谱截图可以上传、识别、编辑和保存。
- [ ] 菜谱可以加入指定日期和餐次。
- [ ] 多道菜的食材可以确定性地合并为采购清单。
- [ ] 采购勾选在弱网或短时离线时不丢失。
- [ ] 临时商品、实际数量和金额可以记录。
- [ ] 采购完成后形成可查看的账单。
- [ ] 做菜记录可以关联菜单和采购账单。
- [ ] 当前账号和同桌档案的评分可以分别保存。
- [ ] 核心错误有明确反馈和恢复路径。
- [ ] 至少一位实际使用者连续使用四周，并记录真实的共同用餐。

### 5.3 非目标

MVP 不以以下能力为完成条件：

- 公开菜谱社区。
- 精确库存与保质期管理。
- 医学级健康建议。
- 完整财务记账。
- 任意小红书链接后台抓取。
- 高级生成式食物修图。
- 好友邀请、多人账号和食堂分组。
- 商店上架和大规模公开获客。

## 6. 实施路线图

每个阶段只有在出口条件满足后才进入下一阶段。阶段内可以根据实践调整顺序。

### 阶段 0：技术预研与工程决策

**目标**：用最小实验消除会导致整体返工的技术不确定性。

任务：

- [ ] `S0.1` 确认首位内部用户的设备、系统版本和开发设备。
- [x] `S0.2` 建立 React Native + Expo 最小实验项目。
- [ ] `S0.3` 在真机验证相册多选、相机、图片压缩和系统分享。
- [ ] `S0.4` 验证 iOS 与 Android 的安全区、底部导航和中文字体。
- [x] `S0.5` 比较并选择后端方案。
- [ ] `S0.6` 用 20–50 组真实截图评测候选 AI 模型。
- [x] `S0.7` 设计最小数据模型和权限策略。
- [ ] `S0.8` 记录最终技术选型及被否决方案。

出口条件：

- 客户端能在目标真机运行。
- 图片输入和分享能力可行。
- 后端与 AI 服务有明确选择。
- 能估算每 100 次菜谱导入的成本。
- 核心数据模型没有明显阻塞。

### 阶段 1：工程底座

**目标**：建立后续功能可以安全迭代的应用骨架。

任务：

- [ ] `S1.1` 初始化正式 App、代码规范和目录结构。
- [ ] `S1.2` 建立开发、测试和生产环境配置。
- [ ] `S1.3` 建立数据库迁移机制。
- [ ] `S1.4` 实现登录、会话恢复和退出。
- [ ] `S1.5` 实现 `profiles`、默认私人食堂和非登录同桌档案。
- [ ] `S1.6` 建立头像及食堂图片上传、缩略图和失败重试。
- [ ] `S1.7` 落地颜色、排版、间距、按钮、卡片和表单组件。
- [ ] `S1.8` 建立日志、错误监控和最小 CI。
- [ ] `S1.9` 实现统一 `PendingOperations` 最小接口，再接入设置页、编辑资料、同桌档案和退出确认。

实现顺序固定为：

```text
S1.4 登录与会话
  → S1.5 profiles、默认食堂、同桌档案
  → S1.6 头像上传
  → S1.9 PendingOperations、设置页、编辑资料、同桌档案、退出确认
```

`S1.7` 和 `S1.8` 可与上述业务链路并行推进，但不得跳过 `S1.4`–`S1.6` 的数据依赖直接堆静态设置页。

出口条件：

- 新用户能登录并自动获得默认私人食堂。
- 用户可以创建、修改和删除未被历史记录引用的同桌档案。
- App 重启后会话与空间不丢失。
- 用户修改昵称后相关页面立即更新，重新登录后仍保留。
- 退出登录会清除本机会话但不会删除云端数据；未同步内容不会静默丢失。
- 内部 MVP 的协议入口可打开本地静态说明；反馈入口在配置支持邮箱时可以调起系统邮件。
- 基础设计组件通过明暗环境和常见屏幕尺寸检查。
- 主分支检查可以自动运行。

### 阶段 2：菜谱仓库与 AI 导入

**目标**：完成从真实截图到可复用菜谱的闭环。

任务：

- [ ] `S2.1` 实现菜谱、食材、步骤和来源数据模型。
- [ ] `S2.2` 实现菜谱仓库列表、搜索和基础筛选。
- [ ] `S2.3` 实现相册选择多张截图。
- [ ] `S2.4` 实现上传进度、取消、失败重试和草稿恢复。
- [ ] `S2.5` 建立服务端 AI 结构化提取接口。
- [ ] `S2.6` 实现 AI 导入确认和不确定项标记。
- [ ] `S2.7` 实现完整菜谱编辑。
- [ ] `S2.8` 实现菜谱详情、份量换算和历史经验区域。
- [ ] `S2.9` 建立固定样本回归评测。

出口条件：

- 真实截图可稳定生成一份可编辑菜谱。
- AI 失败不导致图片或人工修改丢失。
- 用户能看懂哪些字段不确定。
- 至少 80% 的测试样本能在一次确认后保存为可用菜谱；该阈值可根据首轮评测调整。

### 阶段 3：用餐计划、日期和菜单篮

**目标**：把“收藏”推进为某天要执行的做饭计划。

任务：

- [ ] `S3.1` 实现用餐计划及计划菜谱模型。
- [ ] `S3.2` 实现今晚、明天和更多日期选择。
- [ ] `S3.3` 实现有安排日期圆点和已有计划摘要。
- [ ] `S3.4` 实现菜单篮的增删菜、人数、食量和餐次调整。
- [ ] `S3.5` 实现餐桌首页的有菜单和空菜单状态。
- [ ] `S3.6` 实现当前账号与同桌档案的想吃状态。
- [ ] `S3.7` 处理重复餐次、取消计划和过去日期补录。

出口条件：

- 用户可从仓库和详情页把菜加入同一套日期流程。
- 当天已有菜单时不会意外创建重复晚餐。
- 修改人数和食量不会覆盖菜谱原始份量。
- 首页能正确反映用餐计划当前阶段。

### 阶段 4：确定性食材计算与 AI 配餐

**目标**：生成可信的采购输入，并提供有用但不打扰的菜单建议。

任务：

- [ ] `S4.1` 定义标准食材、别名、单位和换算规则。
- [ ] `S4.2` 实现人数与食量的确定性换算。
- [ ] `S4.3` 实现多道菜食材合并和来源拆分。
- [ ] `S4.4` 实现基础菜单构成和份量规则检查。
- [ ] `S4.5` 接入营养数据源并显示估算依据。
- [ ] `S4.6` 实现 AI 配餐解释和具体调整建议。
- [ ] `S4.7` 实现烹饪任务排序与时间冲突提示。
- [ ] `S4.8` 实现“保持原计划”和重新分析。

出口条件：

- 相同输入每次生成相同采购数量。
- 采购项可以追溯到具体菜谱与原始用量。
- 缺失或模糊用量不会被伪装成精确结果。
- AI 建议可执行、可忽略，且不会阻止用户继续。

### 阶段 5：采购清单与采购账单

**目标**：让用户在真实超市场景中完成一次采购并保存支出。

任务：

- [ ] `S5.1` 实现采购行程、采购项和来源映射模型。
- [ ] `S5.2` 实现按区域分组、进度和快速勾选。
- [ ] `S5.3` 实现家里已有、没找到和不买了。
- [ ] `S5.4` 实现实际数量、单位、金额和备注编辑。
- [ ] `S5.5` 实现临时商品与计划外分类。
- [ ] `S5.6` 实现本地即时更新、离线队列和恢复同步。
- [ ] `S5.7` 实现同一账号跨设备的数据恢复，并验证本地与服务端合并。
- [ ] `S5.8` 实现完成采购确认、实付、优惠、商家和付款人。
- [ ] `S5.9` 实现账单详情和更正记录。

出口条件：

- 超市弱网下勾选无明显等待且不会丢失。
- 计划量和实际量分别保存。
- 单项合计与实付差异可以解释。
- 同一账号重新登录或更换设备后能恢复最新采购状态。
- 已完成采购可以追溯到相关用餐计划。

### 阶段 6：做饭模式、记录与分享

**目标**：完成从采购到共同记忆的最后一段。

任务：

- [ ] `S6.1` 实现基础做饭模式和防休眠。
- [ ] `S6.2` 展示 AI 建议的烹饪顺序和计时任务。
- [ ] `S6.3` 实现成品照片上传和基础裁切。
- [ ] `S6.4` 实现主厨、协作者、实际用时和公共短评。
- [ ] `S6.5` 实现当前账号与同桌档案的独立评分和复做意愿。
- [ ] `S6.6` 实现做菜记录保存和菜谱历史更新。
- [ ] `S6.7` 实现餐桌时间线。
- [ ] `S6.8` 实现第一套固定分享模板。
- [ ] `S6.9` 实现系统分享和公开字段确认。

出口条件：

- 不填写同桌评价也可以先保存，之后由当前账号补录。
- 做菜记录能关联菜谱、菜单和采购账单。
- 原始照片与分享成片分别保存。
- 微信等目标应用的分享结果清晰且文案正确。

**目标**：让真实使用决定哪些功能留下、调整或删除。

## 7. 初始系统边界

### 7.1 建议架构

```text
React Native App
├─ 页面与交互
├─ 本地缓存 / 采购离线队列
├─ 图片预处理
└─ 系统相册、相机与分享
          │
          ▼
应用服务 / Server Functions
├─ 权限检查
├─ AI 请求编排
├─ 食材与单位计算
├─ 分享图任务
└─ 日志与限流
          │
          ├─ PostgreSQL：结构化数据
          ├─ Object Storage：截图和照片
          ├─ Sync：单账号跨设备恢复
          ├─ AI Provider：视觉提取与建议
          └─ Nutrition Source：营养基础数据
```

原则：

- AI 密钥只存在于服务端。
- 权限不能只依赖客户端隐藏页面。
- 份量换算、食材合并和金额必须由确定性代码完成。
- AI 输出先通过结构校验，再写入数据库。
- 图片上传使用短期授权，不公开整个存储桶。

### 7.2 初始数据实体

| 实体 | 责任 |
| --- | --- |
| `users` | 用户身份和基础资料 |
| `profiles` | 展示昵称、头像和默认用餐人数；与 `auth.users` 认证身份分离 |
| `table_spaces` | 默认私人食堂；数据结构预留未来分组 |
| `table_members` | 账号与食堂的拥有关系；MVP 每个食堂只有一个账号成员 |
| `diner_profiles` | 非登录同桌档案及其昵称、头像和偏好 |
| `recipes` | 菜谱主数据和原始份量 |
| `recipe_ingredients` | 原始文本、标准食材、数量、单位和确认状态 |
| `recipe_steps` | 有序制作步骤 |
| `recipe_sources` | 来源链接、作者和原始截图 |
| `meal_plans` | 日期、餐次、人数、食量和状态 |
| `meal_plan_recipes` | 用餐计划中的菜及当次调整 |
| `shopping_trips` | 一次采购过程与结算信息 |
| `shopping_items` | 计划量、实际量、金额、状态和计划外标记 |
| `shopping_item_sources` | 采购项与菜谱食材的多对多来源映射 |
| `cooking_records` | 一次实际制作、照片、用时和短评 |
| `cooking_ratings` | 当前账号或同桌档案的独立评分和复做意愿 |
| `media_assets` | 原图、缩略图、美化图和分享图 |

数据模型要点：

- 所有业务数据归属于餐桌空间。
- 认证身份与可编辑用户资料分离；昵称不是登录凭据。
- 菜谱保存原始值与标准化值。
- 菜单保存当次调整，不能覆盖原菜谱。
- 采购项支持来自多个菜谱。
- 采购实付与菜品消耗成本是不同概念。
- 做菜评分的评价主体可以是账号或同桌档案，且二者互斥。
- 同桌档案保留可被未来账号认领的关联位，但 MVP 不实现认领流程。

### 7.3 媒体路径规则

账号头像和食堂业务媒体共用私有 `private-media` 桶，但严格划分路径：

```text
users/{user_id}/avatar/{asset_id}.{ext}
tables/{table_space_id}/diner-avatars/{asset_id}.{ext}
tables/{table_space_id}/recipe-sources/{asset_id}.{ext}
tables/{table_space_id}/recipe-covers/{asset_id}.{ext}
tables/{table_space_id}/cooking-photos/{asset_id}.{ext}
tables/{table_space_id}/receipts/{asset_id}.{ext}
tables/{table_space_id}/share-cards/{asset_id}.{ext}
```

用户头像只允许本人访问；食堂媒体依据成员关系读取。同桌头像属于食堂媒体。完整约束见 [数据模型](data-model.md)。

### 7.4 待同步操作接口

`S1.9` 使用统一 `PendingOperations` 接口汇总采购变更、图片上传和草稿，而不是直接读取各模块内部状态。

- 阶段 1 登记资料草稿与头像上传；尚未实现的采购队列明确返回 0。
- 无法确认状态时返回 `unknown`，退出确认不得显示“可以安全退出”。
- 选择保留并退出时，待同步内容按用户 ID 留在本机，下次同账号登录后继续处理。
- 阶段 5 将采购离线队列接入同一接口，不改变设置页契约。

## 8. AI 实践方案

### 8.1 AI 菜谱提取

建议采用结构化输出，最少包含：

```json
{
  "title": "番茄牛腩",
  "servings": { "text": "3～4 人份", "value": null },
  "ingredients": [
    {
      "name_raw": "生抽",
      "amount_raw": "一大勺",
      "normalized_name": "生抽",
      "quantity": null,
      "unit": null,
      "confidence": "uncertain"
    }
  ],
  "steps": [],
  "warnings": []
}
```

实践原则：

- 保留原文，标准化失败不影响保存。
- 不用模型自己声明的百分比当作真实准确率。
- 对必填字段做服务端结构校验。
- AI 输出不直接覆盖人工修改。
- 每次模型、提示词或结构变化后重跑固定样本集。

### 8.2 AI 评测集

首批样本需要覆盖：

- 单张和多张截图。
- 图文混排、长图和字幕截图。
- 清晰、模糊、裁切不完整和有水印的图片。
- 家常菜、烘焙、汤、凉菜和主食。
- 克、毫升、个、把、勺、碗、适量和少许。
- 同一种食材在多张截图中重复或冲突。

评测指标：

- 菜名正确率。
- 食材召回率和错误新增率。
- 数量、单位正确率。
- 步骤顺序正确率。
- 不确定项识别率。
- 人工确认所需时间。
- 单次成本和端到端延迟。

### 8.3 AI 配餐

实现顺序：

1. 用确定性规则计算人数、菜量、菜类和营养基础数据。
2. 用规则识别明显缺失或冲突。
3. 让 AI 负责解释、排序和生成温和建议。
4. 对推荐菜只允许引用用户仓库中真实存在的菜谱 ID。

AI 不应直接决定：采购数量、最终金额、医疗建议或用户必须吃什么。

## 9. 离线与未来协作实践

采购是最需要优先支持离线的场景。

建议行为：

- 勾选、数量和金额先写本地，再异步同步。
- 每次变更携带项目 ID、字段、版本和修改时间，为未来多端同步预留。
- MVP 优先处理同一账号的断网恢复与重复提交，不实现多人并发冲突界面。
- 状态、数量和金额分字段更新，降低未来多人化的迁移成本。
- 删除采用软删除或撤销窗口。
- 网络恢复后显示简短同步结果，不阻塞继续采购。

MVP 必须真机验证：

1. 用户打开清单后断网。
2. 离线勾选项目并修改金额。
3. 用户恢复网络并重启 App。
4. 状态和金额都应保留，且不产生重复采购项。

好友与分组阶段再验证：邀请与认领、多人同时编辑、成员退出和数据归属。

## 11. 隐私、安全与版权

从第一版开始执行：

- 默认所有餐桌、账单、健康和照片数据均为私人。
- 每个服务端请求验证用户是否属于目标餐桌空间。
- AI 和存储密钥不进入客户端包和版本库。
- 日志不记录原始图片、完整菜谱内容、账单详情和认证令牌。
- 支持删除账号或餐桌数据的实现路径，即使首个内部版本暂不开放按钮。
- 菜谱保留来源链接、作者信息和原始截图。
- 公开分享不默认包含完整步骤、账单或个人健康信息。
- AI 美化内容与原始照片分开保存并明确标识。

需要在公开测试前补齐：隐私政策、用户协议、第三方服务清单、数据保留规则和账号注销流程。

## 17. 决策日志

### D-001 · 以纵向闭环组织 MVP

- 日期：2026-10-22
- 状态：已接受
- 背景：产品横跨菜谱、菜单、健康、采购、记账、点评和分享，若按模块横向开发容易长期无法真实使用。
- 选择：优先实现“截图导入—今晚菜单—采购—做菜记录”的最小纵向闭环。
- 备选：先完成所有 Figma 页面；先建设完整菜谱库；先做公开社区。
- 理由：纵向闭环能最早进入真实生活场景，也能暴露模块之间的数据问题。
- 后果：部分页面和高级能力会暂时简化，但可以更早开始内部试用。
- 复审条件：核心闭环被真实使用至少四周后。

### D-002 · 以原始值和标准值共同保存食材

- 日期：2026-10-22
- 状态：已接受
- 背景：中式菜谱经常包含“一勺”“适量”等无法可靠精确换算的用量。
- 选择：同时保存原始文本、标准化食材、数值、单位和人工确认状态。
- 备选：只保存 AI 标准化结果；完全不做标准化。
- 理由：既保留来源真实性，又支持后续合并与营养计算。
- 后果：数据模型更复杂，但避免 AI 猜测污染原始菜谱。
- 复审条件：真实样本证明此结构无法覆盖主要用量表达时。

### D-003 · 采购清单采用离线优先

- 日期：2026-10-22
- 状态：提议
- 背景：超市网络可能不稳定，勾选是高频且不能等待的操作。
- 选择：采购变更先写本地，再异步同步到服务端。
- 备选：所有操作实时请求服务端；整个 App 全量离线优先。
- 理由：聚焦最需要离线的场景，兼顾体验与工程复杂度。
- 后果：需要本地队列、字段级同步和冲突处理。
- 复审条件：阶段 0 技术实验确认本地数据方案后。

### D-004 · 客户端采用 React Native + Expo

- 日期：2026-10-22
- 状态：提议
- 背景：产品需要相册、相机、系统分享、通知和弱网能力，同时希望兼顾 iOS 与 Android。
- 选择：优先验证 React Native + Expo + TypeScript。
- 备选：原生 iOS；Flutter；PWA。
- 理由：预期能用一套代码快速交付内部版本，并覆盖所需原生能力。
- 后果：需先验证关键原生能力和依赖兼容性，验证前不标记为最终选型。
- 复审条件：完成 `S0.2`–`S0.4` 后。

### D-005 · MVP 采用单账号和非登录同桌档案

- 日期：2026-10-22
- 状态：已接受
- 背景：首版的核心目标是验证菜谱、菜单、采购和记录闭环；双账号邀请、权限和实时同步会显著扩大范围。
- 选择：MVP 只实现一个登录账号。账号拥有默认私人食堂，并可创建非登录同桌档案，由账号代录想吃、主厨、付款人和评分。
- 备选：首版直接支持两个账号；完全删除关系角色，只记录单人信息。
- 理由：减少认证、邀请、权限、实时冲突和通知成本，同时保留情侣或家庭场景的关系感。
- 后果：首版无法让另一位用户用自己的手机独立操作；评价属于代录。数据模型需让同桌档案未来可被注册账号认领。
- 复审条件：单账号闭环稳定使用，且出现明确的跨设备共同编辑需求后。

### D-006 · MVP 后端采用 Supabase

- 日期：2026-10-22
- 状态：已接受
- 背景：MVP 需要认证、关系数据、私有图片存储、服务端 AI 编排和可演进的成员权限，同时希望减少基础设施数量。
- 选择：采用 Supabase，项目优先部署在 Singapore 区域；内部 MVP 从 Free Plan 开始。
- 备选：Firebase、Appwrite、自建 PostgreSQL 与对象存储。
- 理由：Supabase 的 PostgreSQL、Auth、Storage、RLS 和 Edge Functions 与当前数据模型直接匹配，Expo React Native 也有官方集成路径。
- 后果：业务表和私有图片必须从第一天建立严格 RLS；中国大陆没有本地区域，需在目标手机日常网络下验证 Singapore 的可用性。
- 复审条件：目标网络测试持续失败或延迟不可接受；合规或数据位置要求发生变化；实际费用超出内部试用预算。
- 详细评估：[后端方案评估](backend-evaluation.md)。

### D-007 · 用户设置作为二级页面而非底部导航

- 复审条件：后续好友分组上线，账号与分组切换成为高频任务时。

### D-008 · 账号头像与食堂媒体共用私有桶并分命名空间

- 日期：2026-10-22
- 状态：已接受
- 背景：用户头像属于账号，菜谱、同桌头像、做菜照片和小票属于食堂，二者不能只用食堂 UUID 作为统一路径根。
- 选择：共用私有 `private-media` 桶；账号头像使用 `users/{user_id}/avatar/...`，食堂媒体使用 `tables/{table_space_id}/{media_type}/...`，分别配置 RLS。
- 备选：建立单独公开头像桶；所有媒体继续使用食堂 UUID 根目录。
- 理由：保持单一私有媒体基础设施，同时正确表达账号和食堂两种归属，避免用户头像随某个食堂权限变化。
- 后果：Storage 策略更细；客户端必须通过统一路径构造器生成路径。
- 复审条件：未来需要公开头像或 CDN 直链时。

- 备选：阶段 1 不检查未同步数据；提前实现完整采购离线队列。
- 理由：以稳定接口解耦设置页和后续业务模块，既不伪造安全状态也不扩大阶段 1 范围。
- 后果：本地持久化从阶段 1 就必须按用户隔离；未知状态需要专门的退出提示。
- 复审条件：本地状态架构确定后，如有更合适的统一任务队列实现。

## 20. 文档维护规则

- 开始一个任务时，将其放入“正在进行”。
- 完成后勾选路线图任务，并在实践日志追加记录。
- 改变产品行为时，同步更新产品原型文档。
- 改变长期技术选择时，在决策日志新增记录；不要删除旧决策。
- 新方案替代旧方案时，将旧决策标为“已替换”并链接新决策编号。
- 每次版本或里程碑结束时更新顶部版本号和日期。
- 保留失败实验和被否决方案，它们同样是项目知识。
- 日志采用追加方式，最新内容放在对应章节顶部或维护清晰的日期顺序。
