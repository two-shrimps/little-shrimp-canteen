> 版本：v0.1

> 当前阶段：从产品原型进入工程实现  
> 文档性质：持续更新的执行手册、进度记录与决策日志

## 1. 文档目的

这份文档用于指导 Little Shrimp Canteen 从原型走向可使用的 App，并持续记录实施过程中的方案调整、实验结果、技术决策和未解决问题。

它不是一次写完后不再变化的技术方案，而是项目的“实践账本”。每完成一个步骤，我们都应该在这里留下：

- 做了什么。
- 为什么这样做。
- 如何验证。
- 结果是否符合预期。
- 哪些产品或技术假设发生了变化。
- 下一步是什么。

最终目标不是按原计划完成所有功能，而是持续缩短这条真实闭环：

```text
小红书菜谱截图
      ↓
AI 整理并人工确认
      ↓
加入今晚或其他日期的菜单
      ↓
生成并完成采购清单
      ↓
保存做菜照片和双人评价
      ↓
在餐桌时间线中留下记录
```

## 3. 协作与记录原则

### 3.1 一次只推进一个可验证步骤

每个步骤应该小到可以明确判断完成或失败。避免一次同时实现整个菜单、采购和分享系统。

推荐节奏：

```text
选择一个小目标 → 写清验收标准 → 实现 → 自动验证 → 真机体验
               → 记录结果与调整 → 选择下一步
```

### 3.2 纵向闭环优先于横向完整

优先让一条简单流程真正可用，再增加各模块的高级能力。第一条闭环可以只支持：

- 一个餐桌空间。
- 两个固定测试用户。
- 从相册选择截图。
- 人工确认 AI 结果。
- 一顿晚餐。
- 手动采购勾选与金额。
- 一张成品照片和一个综合评分。

### 3.3 方案状态必须显式标记

本文档中的重要方案使用以下状态：

| 状态 | 含义 |
| --- | --- |
| `已确定` | 已经过讨论或实践验证，按此实施 |
| `暂定` | 当前默认方案，可以先做，但仍可能调整 |
| `待验证` | 需要用原型、代码或真实用户验证 |
| `已否决` | 明确不采用，并保留原因 |
| `已替换` | 曾经采用，后来被新方案取代 |

### 3.4 不静默改变产品行为

实现中遇到以下情况时，需要更新产品原型文档或本文档：

- 页面流程发生变化。
- 字段含义或必填规则变化。
- AI 能力边界变化。
- MVP 范围增加或删除。
- 数据模型迫使产品行为改变。
- 真机使用证明原设计不好用。

小型代码重构、内部命名和不影响体验的实现细节无需上升为产品决策。

### 3.5 每一步必须有验证

根据变更类型至少完成一种验证：

- 业务逻辑：单元测试。
- 数据读写：集成测试和迁移测试。
- 页面交互：组件测试或端到端测试。
- 相机、相册、分享和通知：真机测试。
- AI 输出：固定样本评测和人工复核。
- 视觉：与 Figma 对照并检查不同屏幕尺寸。

## 5. MVP 成功标准

第一版不是以页面数量验收，而是以真实任务验收。

### 5.1 核心验收故事

> 用户从相册选择一组小红书菜谱截图，AI 提取菜名、食材和步骤；用户修正不确定项并保存，将菜谱加入今晚菜单。系统按照两人份生成合并后的采购清单。两个人可以边买边勾选、补充临时商品和记录金额。做完后上传照片、分别评分，并在餐桌历史中再次找到这次记录。

### 5.2 MVP 完成条件

- [ ] 至少两台真实手机可以登录同一个餐桌空间。
- [ ] 菜谱截图可以上传、识别、编辑和保存。
- [ ] 菜谱可以加入指定日期和餐次。
- [ ] 多道菜的食材可以确定性地合并为采购清单。
- [ ] 采购勾选在弱网或短时离线时不丢失。
- [ ] 临时商品、实际数量和金额可以记录。
- [ ] 采购完成后形成可查看的账单。
- [ ] 做菜记录可以关联菜单和采购账单。
- [ ] 两个人的评分分别保存。
- [ ] 核心错误有明确反馈和恢复路径。
- [ ] 两位实际使用者连续使用至少四周。

### 5.3 非目标

MVP 不以以下能力为完成条件：

- 公开菜谱社区。
- 精确库存与保质期管理。
- 医学级健康建议。
- 完整财务记账。
- 任意小红书链接后台抓取。
- 高级生成式食物修图。
- 商店上架和大规模公开获客。

## 7. 初始系统边界

### 7.1 建议架构

```text
React Native App
├─ 页面与交互
├─ 本地缓存 / 采购离线队列
├─ 图片预处理
└─ 系统相册、相机与分享
          │
          ▼
应用服务 / Server Functions
├─ 权限检查
├─ AI 请求编排
├─ 食材与单位计算
├─ 分享图任务
└─ 日志与限流
          │
          ├─ PostgreSQL：结构化数据
          ├─ Object Storage：截图和照片
          ├─ Realtime：双人协作
          ├─ AI Provider：视觉提取与建议
          └─ Nutrition Source：营养基础数据
```

原则：

- AI 密钥只存在于服务端。
- 权限不能只依赖客户端隐藏页面。
- 份量换算、食材合并和金额必须由确定性代码完成。
- AI 输出先通过结构校验，再写入数据库。
- 图片上传使用短期授权，不公开整个存储桶。

### 7.2 初始数据实体

| 实体 | 责任 |
| --- | --- |
| `users` | 用户身份和基础资料 |
| `table_spaces` | 私人餐桌空间 |
| `table_members` | 用户与餐桌的成员关系和角色 |
| `recipes` | 菜谱主数据和原始份量 |
| `recipe_ingredients` | 原始文本、标准食材、数量、单位和确认状态 |
| `recipe_steps` | 有序制作步骤 |
| `recipe_sources` | 来源链接、作者和原始截图 |
| `meal_plans` | 日期、餐次、人数、食量和状态 |
| `meal_plan_recipes` | 用餐计划中的菜及当次调整 |
| `shopping_trips` | 一次采购过程与结算信息 |
| `shopping_items` | 计划量、实际量、金额、状态和计划外标记 |
| `shopping_item_sources` | 采购项与菜谱食材的多对多来源映射 |
| `cooking_records` | 一次实际制作、照片、用时和短评 |
| `cooking_ratings` | 每位成员独立评分和复做意愿 |
| `media_assets` | 原图、缩略图、美化图和分享图 |

数据模型要点：

- 所有业务数据归属于餐桌空间。
- 菜谱保存原始值与标准化值。
- 菜单保存当次调整，不能覆盖原菜谱。
- 采购项支持来自多个菜谱。
- 采购实付与菜品消耗成本是不同概念。
- 做菜评分按成员独立存储。

## 8. AI 实践方案

### 8.1 AI 菜谱提取

建议采用结构化输出，最少包含：

```json
{
  "title": "番茄牛腩",
  "servings": { "text": "3～4 人份", "value": null },
  "ingredients": [
    {
      "name_raw": "生抽",
      "amount_raw": "一大勺",
      "normalized_name": "生抽",
      "quantity": null,
      "unit": null,
      "confidence": "uncertain"
    }
  ],
  "steps": [],
  "warnings": []
}
```

实践原则：

- 保留原文，标准化失败不影响保存。
- 不用模型自己声明的百分比当作真实准确率。
- 对必填字段做服务端结构校验。
- AI 输出不直接覆盖人工修改。
- 每次模型、提示词或结构变化后重跑固定样本集。

### 8.2 AI 评测集

首批样本需要覆盖：

- 单张和多张截图。
- 图文混排、长图和字幕截图。
- 清晰、模糊、裁切不完整和有水印的图片。
- 家常菜、烘焙、汤、凉菜和主食。
- 克、毫升、个、把、勺、碗、适量和少许。
- 同一种食材在多张截图中重复或冲突。

评测指标：

- 菜名正确率。
- 食材召回率和错误新增率。
- 数量、单位正确率。
- 步骤顺序正确率。
- 不确定项识别率。
- 人工确认所需时间。
- 单次成本和端到端延迟。

### 8.3 AI 配餐

实现顺序：

1. 用确定性规则计算人数、菜量、菜类和营养基础数据。
2. 用规则识别明显缺失或冲突。
3. 让 AI 负责解释、排序和生成温和建议。
4. 对推荐菜只允许引用用户仓库中真实存在的菜谱 ID。

AI 不应直接决定：采购数量、最终金额、医疗建议或用户必须吃什么。

## 9. 离线与双人协作实践

采购是最需要优先支持离线的场景。

建议行为：

- 勾选、数量和金额先写本地，再异步同步。
- 每次变更携带项目 ID、字段、版本和修改时间。
- 同一字段冲突默认采用最后一次有效修改，同时保留上一值用于恢复。
- 状态和数量分开更新，避免一次操作覆盖对方刚输入的金额。
- 删除采用软删除或撤销窗口。
- 网络恢复后显示简短同步结果，不阻塞继续采购。

必须真机验证：

1. 两台手机同时打开同一清单。
2. A 断网勾选，B 在线修改金额。
3. A 恢复网络。
4. 状态和金额都应保留，且不产生重复采购项。

## 10. 测试与质量策略

### 10.1 测试分层

- 单元测试：份量、单位、食材合并、金额和状态机。
- 集成测试：认证、餐桌权限、数据库迁移、上传和 AI 结构校验。
- 组件测试：表单、不确定项、筛选、清单行和错误反馈。
- 端到端测试：导入到记录的核心闭环。
- 真机测试：相册、相机、分享、通知、离线和实时同步。
- 视觉回归：核心页面与 Figma 对照。

### 10.2 每次变更的最低检查

- 类型检查通过。
- 受影响的单元或组件测试通过。
- 没有明显控制台错误。
- 至少手动走通本次修改的主路径。
- 若修改数据结构，验证旧数据迁移或明确不兼容策略。

### 10.3 完成定义

任务只有同时满足以下条件才标记完成：

- 功能行为符合当前文档。
- 正常、空、加载、失败和重试状态已考虑。
- 权限和数据归属正确。
- 相关测试通过。
- 已在目标设备或合理替代环境中验证。
- 必要的方案调整已记录。

## 11. 隐私、安全与版权

从第一版开始执行：

- 默认所有餐桌、账单、健康和照片数据均为私人。
- 每个服务端请求验证用户是否属于目标餐桌空间。
- AI 和存储密钥不进入客户端包和版本库。
- 日志不记录原始图片、完整菜谱内容、账单详情和认证令牌。
- 支持删除账号或餐桌数据的实现路径，即使首个内部版本暂不开放按钮。
- 菜谱保留来源链接、作者信息和原始截图。
- 公开分享不默认包含完整步骤、账单或个人健康信息。
- AI 美化内容与原始照片分开保存并明确标识。

需要在公开测试前补齐：隐私政策、用户协议、第三方服务清单、数据保留规则和账号注销流程。

## 17. 决策日志

### D-001 · 以纵向闭环组织 MVP

- 日期：2026-10-22
- 状态：已接受
- 背景：产品横跨菜谱、菜单、健康、采购、记账、点评和分享，若按模块横向开发容易长期无法真实使用。
- 选择：优先实现“截图导入—今晚菜单—采购—做菜记录”的最小纵向闭环。
- 备选：先完成所有 Figma 页面；先建设完整菜谱库；先做公开社区。
- 理由：纵向闭环能最早进入真实生活场景，也能暴露模块之间的数据问题。
- 后果：部分页面和高级能力会暂时简化，但可以更早开始内部试用。
- 复审条件：核心闭环被真实使用至少四周后。

### D-002 · 以原始值和标准值共同保存食材

- 日期：2026-10-22
- 状态：已接受
- 背景：中式菜谱经常包含“一勺”“适量”等无法可靠精确换算的用量。
- 选择：同时保存原始文本、标准化食材、数值、单位和人工确认状态。
- 备选：只保存 AI 标准化结果；完全不做标准化。
- 理由：既保留来源真实性，又支持后续合并与营养计算。
- 后果：数据模型更复杂，但避免 AI 猜测污染原始菜谱。
- 复审条件：真实样本证明此结构无法覆盖主要用量表达时。

### D-003 · 采购清单采用离线优先

- 日期：2026-10-22
- 状态：提议
- 背景：超市网络可能不稳定，勾选是高频且不能等待的操作。
- 选择：采购变更先写本地，再异步同步到服务端。
- 备选：所有操作实时请求服务端；整个 App 全量离线优先。
- 理由：聚焦最需要离线的场景，兼顾体验与工程复杂度。
- 后果：需要本地队列、字段级同步和冲突处理。
- 复审条件：阶段 0 技术实验确认本地数据方案后。

### D-004 · 客户端采用 React Native + Expo

- 日期：2026-10-22
- 状态：提议
- 背景：产品需要相册、相机、系统分享、通知和弱网能力，同时希望兼顾 iOS 与 Android。
- 选择：优先验证 React Native + Expo + TypeScript。
- 备选：原生 iOS；Flutter；PWA。
- 理由：预期能用一套代码快速交付内部版本，并覆盖所需原生能力。
- 后果：需先验证关键原生能力和依赖兼容性，验证前不标记为最终选型。
- 复审条件：完成 `S0.2`–`S0.4` 后。
